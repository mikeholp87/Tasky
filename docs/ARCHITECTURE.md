# Architecture

Task Manager is a Tauri 2 desktop app. A Rust backend samples the operating
system; a React frontend renders what it is sent. This document explains how
the pieces fit and why they are shaped this way.

## Key decisions

### One monitoring engine, one thread

Only `tm_core::monitoring::Engine` queries the OS for metrics. It runs on a
dedicated thread that owns the `sysinfo` handles, so they never need locks.
The thread sleeps with `recv_timeout` on a control channel, and while
monitoring is paused it blocks indefinitely, using no CPU.

Each tick:

1. `Collector::sample` refreshes CPU, memory, disks (I/O and capacity every
   tick, mount list every 30 s), networks and processes, and measures the real
   elapsed time.
2. `AlertEvaluator` checks rules against the sample.
3. Results are published to shared state under short write locks: latest
   tick, system history ring, per-process history ring, alert log.
4. The tick is delivered to every `TickSink`. JSON is serialized **once**, and
   only if a sink wants it.

Static information (OS, CPU model, core counts) is read once at startup.

_Why:_ the brief requires a single source of truth and no duplicate polling.
Owning the OS handles on one thread also keeps lock contention to a few
microseconds per tick.

### `tm-core` has no Tauri dependency

Models, monitoring, platform code and process control live in a separate
crate. The Tauri crate only adapts IPC, the tray and settings files.

_Why:_ the core can be unit- and integration-tested without a window, and it
can be **type-checked and linted for Linux from Windows**
(`npm run check:linux`). Tauri's GTK build scripts cannot be cross-compiled,
so that check is not possible for the app crate.

### Platform abstraction

`platform/mod.rs` is the only file with `#[cfg(target_os)]` dispatch. Each OS
module implements the same free functions (`memory_extras`, `process_extras`,
`connections`, `disk_io_counters`, `terminate`, `suspend`, …). macOS has stubs
that compile and report "unavailable", so a macOS port fills in one module
without touching callers. The `/proc` parsers are plain functions compiled on
every OS in tests, so CI on Windows exercises them too.

### Typed IPC, generated types

Every model derives `ts_rs::TS` (test builds only), and `cargo test` writes
TypeScript definitions to `src/types/generated/`. The frontend's `ipc.ts`
wraps each command with typed arguments and results. Errors cross the
boundary as `{ kind, message }`. `ErrorKind` is a closed set; the frontend
maps it with an exhaustive `Record`, so adding a kind is a compile error until
it is handled.

### Ticks over a Tauri `Channel`

The frontend subscribes once with a `Channel`; the engine pushes JSON to it.
Re-subscribing (e.g. after a reload) replaces the sink keyed by webview label,
so stale channels are never leaked. While the window is hidden or minimized
the sink reports `wants_json() == false`. The engine then skips
serialization, and the UI backfills the gap from `get_history` when it
becomes visible again.

### Frontend state

- `metricsStore` holds the latest tick. Selectors keep re-renders scoped.
- History lives in **mutable** bounded buffers (`HistoryBuffer`,
  `DeviceHistory`) plus a version counter, so 1 h of points is not copied on
  every tick.
- Pure logic (filtering, sorting, tree building, alert rule validation,
  formatting) lives in plain `.ts` modules with unit tests. Components
  render; services coordinate with the backend.

### Charts

uPlot (canvas, ~50 KB) is used instead of Recharts. The Performance and CPU
pages can show dozens of live series; uPlot redraws them with `setData`
without re-creating DOM, which keeps frontend CPU low.

### Process table

`@tanstack/react-virtual` renders only visible rows (≈35 of 5,000), keyed by
PID. Filtering and sorting run once per tick in a memoized selector; the
5,000-row case is covered by tests.

### On-demand inspection

Ports, open files, modules, memory maps, threads and the file finder are not
part of the tick. Each is a Tauri command (`commands/inspect.rs`) that runs the
platform function (`platform::sockets`, `open_files`, `find_file_users`,
`memory_map`, `modules`, `threads`) on a blocking worker, and the matching UI
calls it only while it is mounted (`useRemoteData`). Platform code gathers raw
facts; classification, summaries and per-thread CPU percentages live in
`core/src/inspect.rs`, compiled and tested on every OS. The thread sampler keeps
the previous reading of one process only.

### Activity timeline

`monitoring/activity.rs` compares successive process snapshots keyed by
`(pid, start_time)` (so a reused PID is an exit plus a start), applies a
minimum duration and hysteresis to CPU spikes, and tracks memory growth against
a 30-second low-water mark. The engine also records alerts, actions made
through `process_control::perform` and benchmark start/finish. New events ride
in `MetricsTick.activity`; `get_activity(after)` backfills after the window was
hidden. The log is in memory, bounded to 1,000 events. The same detector keeps
one sample per minute (at most 60) per process to report sustained memory or
thread-count growth once per process instance.

## Data flow for an action (e.g. "Force end")

1. Context menu → `requestAction(row, { type: "forceKill" })`.
2. `assess_process_action` returns allowed / warning / blocked with reasons.
3. The confirmation dialog shows the reasons. Blocked actions have no confirm
   button.
4. `perform_process_action(pid, startTime, action, acknowledgeWarnings)`.
   The backend re-checks everything: the PID must still belong to a process
   with that start time, protection rules are re-evaluated, and warnings must
   be acknowledged. Only then does it call the platform function.
5. The engine refreshes immediately so the UI reflects the result.

## Settings

Settings are owned by Rust (`src-tauri/src/settings.rs`) and stored as JSON in
the app config directory:

- Written atomically (temp file + rename).
- Validated on every update.
- Sanitized on load, so a hand-edited file degrades gracefully. A corrupt file
  is moved aside and defaults are used.

Updates apply at runtime: interval, history size, alert rules, notifications,
debug logging and autostart.

## Extending

- **New metric:** add fields to a model in `core/src/models`, collect them in
  `monitoring/`, run `npm run gen:types`, render them in a feature folder.
- **New platform capability:** add the function to every `platform/*`
  module (stub where unsupported) and re-export it from `platform/mod.rs`.
- **GPU and temperatures:** sysinfo's `component` and `gpu` features are enabled.
  `monitoring/sensors.rs` refreshes readings periodically; System Information
  displays them. Battery information is collected on demand through the platform
  layer. Adding live history requires extending the bounded history models.
- **Process history persistence (SQLite):** subscribe a new `TickSink` that
  writes sampled rows with a retention policy. The engine needs no changes.
